# CODEX ORCHESTRATOR — мега-план производства игры Павла

**Дата:** 28 августа 2026  
**Оркестратор:** Codex  
**Исполнители:** Grok Build 4.6 Medium в авторизованном Codex Browser и Cursor
с Grok 4.6 High через Computer Use  
**Источник производственного контракта:**
`docs/prompts/GROK_BUILD_PAVEL_OBSERVATION_BOOTH_PRODUCTION_PLAN.md`

---

## 0. Зачем проводится эксперимент

Проверить гипотезу:

> один осознанный оркестратор, который выдаёт короткие ограниченные задания,
> проверяет фактический результат и передаёт следующему агенту только нужный
> контекст, может оказаться быстрее, дешевле по токенам и надёжнее ручного
> метания между несколькими окнами.

Эксперимент считается успешным не потому, что три модели «поговорили», а если:

- пользователь не переносит вручную промпты, ответы и диффы между окнами;
- каждый исполнитель получает только релевантный пакет контекста;
- нет одновременного редактирования одних файлов;
- Codex независимо проверяет результат каждого этапа;
- старые игры, Copy Desk, сохранения и пользовательские изменения не
  повреждены;
- можно измерить время, количество возвратов и объём человеческого участия;
- ни один сервис не делает commit, push или публикацию без отдельной просьбы.

## 1. Реализуемость и главное ограничение

Схема технически реализуема:

1. Codex управляет авторизованным Grok через встроенный браузер Codex.
2. Codex управляет установленным Cursor как Mac-приложением через Computer
   Use.
3. Codex читает репозиторий и выполняет независимые локальные проверки через
   терминал.

Grok Build, Cursor и Codex работают с одной локальной папкой
`/Users/nateglukhov/analog-horror-site`. Общей памяти чатов у них нет.
Единственным источником истины остаются:

- текущие файлы этой папки, включая незакоммиченный diff;
- `git status` и `git diff`;
- живой журнал смены `docs/AGENT_STATUS.md` (этап, write-замок, блокеры);
- утверждённый production plan как контракт, а не как текущий статус.

GitHub не используется как канал синхронизации между агентами. Не подключать
Grok к GitHub, не выдавать OAuth и не создавать ключи без отдельного
подтверждения пользователя.

## 2. Роли

### Codex — продюсер, диспетчер и независимая приёмка

Codex:

- читает `docs/AGENT_STATUS.md`, `AGENTS.md`, канон, production plan и актуальное состояние Git;
- фиксирует разрешённый scope конкретного этапа;
- собирает малый task packet вместо передачи всей истории чата;
- открывает Grok во встроенном браузере и отправляет задание;
- отслеживает его ответ, вопросы, прогресс и итоговые артефакты;
- самостоятельно проверяет утверждения Grok по репозиторию;
- формирует для Cursor пакет интеграции на основе фактов и диффа;
- ведёт Cursor через интерфейс, читая его актуальный статус после действий;
- запускает локальные валидаторы и реальный browser QA;
- останавливает конвейер на пользовательских approval gates;
- не исправляет драматургические неопределённости техническим вымыслом.

Codex не должен быть «почтальоном», бездумно пересылающим полный ответ одной
модели другой. Его функция — сжимать, отбрасывать неподтверждённое и превращать
результат в проверяемое следующее задание.

### Grok Build 4.6 Medium — быстрый изолированный изготовитель

Grok получает один ограниченный этап и правит ту же локальную папку сайта,
что Cursor и Codex. GitHub-коннектор не использовать.

- Stage 0: технический read-only аудит;
- Stage 1: content contract, Copy Desk, validator;
- после отдельного допуска: изолированный MVP новой механики с placeholders.

Grok не получает права:

- менять общую интеграцию сайта без отдельного этапа;
- придумывать служебный ID, личность голоса в сливе или новый канон;
- переписывать большой runtime «для чистоты»;
- генерировать платные медиа;
- делать commit, push, deploy;
- объявлять UI проверенным только по чтению кода.

### Cursor + Grok 4.6 High — локальный интегратор и регрессионный инженер

Cursor получает уже проверенный результат Grok и точный integration packet:

- аудит чужого диффа перед правками;
- интеграция «Солнышка», STAFF/ID, dossier, persistence и `SOURCE`;
- осторожное подключение runtime к content-модулям;
- устранение конфликтов с существующими механиками;
- desktop и `390x844` QA;
- исправление только подтверждённых дефектов.

Cursor не должен заново изобретать драматургию, заменять утверждённые реплики
или расширять scope из-за «полезного рефакторинга».

### Пользователь — режиссёр и владелец необратимых решений

Только пользователь утверждает:

- переход между производственными этапами;
- финальные реплики и канонические неопределённости;
- служебный ID;
- платную генерацию ElevenLabs, изображений и видео;
- точный список production media;
- commit, push и публикацию.

## 3. Транспорт контекста между агентами

Для каждого этапа Codex формирует task packet не длиннее необходимого. В нём
обязательны:

1. одна цель;
2. список разрешённых файлов;
3. список запрещённых действий;
4. канонические ограничения;
5. ожидаемый формат результата;
6. команды проверки;
7. условие остановки.

Передавать следующему агенту нужно не весь чат, а:

- утверждённые решения;
- список реально изменённых файлов;
- компактный diff summary;
- полный локальный `git diff` как источник фактов, если исполнитель может его
  прочитать;
- результаты тестов с exit code;
- открытые ошибки и вопросы;
- запрет повторно решать уже закрытые вопросы.

Содержимое браузерного ответа считается предложением, пока Codex не подтвердил
его по файлам и тестам.

---

## 4. Машина состояний одного этапа

Каждый этап проходит одинаковую последовательность:

```text
PREPARED
  -> DISPATCHED_TO_GROK
  -> GROK_RETURNED
  -> CODEX_AUDITED
  -> USER_GATE (если этап только исследовательский)
  -> DISPATCHED_TO_CURSOR
  -> CURSOR_RETURNED
  -> CODEX_VERIFIED
  -> USER_ACCEPTED
```

Правила:

- одновременно редактирует только один исполнитель;
- новый исполнитель не открывается для записи, пока предыдущий результат не
  зафиксирован и проверен;
- отсутствие ответа, зависший UI или потеря браузерной сессии не меняют статус
  этапа на `DONE`;
- текст «готово» в интерфейсе агента не является доказательством;
- при неожиданном diff этап переводится в `PAUSED — SCOPE VIOLATION`;
- при канонической неопределённости этап переводится в
  `BLOCKED FOR CONTENT`, а не заполняется placeholder как production-факт.

## 5. Нулевой пилот: доказать саму оркестрацию

До реализации игры провести маленький безопасный прогон.

### 5.1 Preflight Codex

Codex фиксирует:

- `git status --short`;
- текущую ветку;
- список пользовательских изменений;
- наличие production plan;
- доступность авторизованного Grok во встроенном браузере;
- доступность Cursor и его текущий workspace;
- отсутствие необходимости передавать секреты или выдавать новые разрешения.

На этом шаге ничего не редактировать.

### 5.2 Задание Grok

Отправить только Stage 0 из production plan. Попросить:

- read-only аудит Copy Desk и маршрута Ирина -> «Солнышко» -> STAFF;
- таблицу confirmed / hypothesis / open decision;
- точный список потенциальных файлов;
- никаких изменений.

### 5.3 Независимая проверка Codex

Codex проверяет выборочно минимум пять утверждений Grok по исходникам. Ошибки
не замалчиваются: они попадают в краткий audit note.

### 5.4 Задание Cursor

Cursor получает не исходный ответ Grok, а очищенный пакет Codex и выполняет
второй read-only аудит тех же рискованных точек:

- surgical save Copy Desk;
- persistence keys;
- текущий `SOURCE`;
- мобильные риски;
- возможные конфликты общих файлов.

### 5.5 Решение о продолжении

Пилот успешен, если оба интерфейса управляются стабильно, отчёты можно
независимо проверить, репозиторий не изменился и пользователь не переносил
контент вручную. Только после этого запускать производство.

## 6. Производственный конвейер

### Волна A — архитектурный контракт

1. Codex извлекает из Stage 0 подтверждённые факты.
2. Пользователь утверждает `CONTENT CONTRACT`.
3. Grok Build Medium создаёт только разрешённый Stage 1.
4. Codex проверяет diff, roundtrip, validators и существующие smoke.
5. Cursor High проводит adversarial audit результата Grok и исправляет только
   подтверждённые проблемы после допуска.
6. Codex повторяет все проверки на итоговом рабочем дереве.

### Волна B — парк «Солнышко»

1. Codex и пользователь фиксируют текст короткой встречи с Ириной.
2. Grok может подготовить изолированный content-модуль и тестовые fixtures.
3. Codex проверяет, что сценарий редактируется через современный Copy Desk.
4. Cursor интегрирует открытку, ввод даты, сохранение разблокировки, STAFF/ID,
   video slot, poster и fallback.
5. Codex проверяет Аниматора, Волонтёра и чистый сеанс на desktop и `390x844`.

### Волна C — MVP кабинки Павла

1. Grok реализует изолированный вертикальный срез:
   `звук -> комната -> предмет -> изменение -> возврат к мониторам`.
2. В нём используются placeholders, существующие SFX и короткий тестовый граф.
3. Codex проверяет механику, доступность без звука, persistence и границы
   контента.
4. Cursor интегрирует MVP с общей навигацией и устраняет регрессии.
5. Codex проводит реальный event-driven browser QA.

### Волна D — полный сценарий и ручные медиа

1. Пользователь вручную генерирует и отбирает изображения/видео.
2. ElevenLabs запускается только после отдельного preflight и утверждения
   текста голоса.
3. Cursor пакует только утверждённые файлы, добавляет poster/fallback и
   интегрирует их без замены исходников.
4. Codex проверяет форматы, размеры, длительность, ссылки, reduced motion,
   sound-off и отсутствующий media fallback.

### Волна E — кассета и финальная регрессия

1. Cursor подключает сохранённую кассету к существующему `SOURCE`.
2. Codex проверяет состояния до находки, после находки, insert, ended, replay,
   reload и возврат к обычному эфиру.
3. Проверяются обе старые игры, STAFF, dossier, Copy Desk, desktop и mobile.
4. Формируется release report без commit/push.
5. Публикация остаётся отдельным пользовательским решением.

## 7. Управление Grok через Codex Browser

На каждом обращении Codex:

1. использует именно встроенный браузер Codex;
2. переиспользует авторизованную вкладку Grok, если она актуальна;
3. перед отправкой сверяет выбранную модель и режим;
4. вставляет один cohesive task packet;
5. после отправки читает фактическое состояние страницы и ответ;
6. при вопросе Grok отвечает только из утверждённого контекста;
7. скачивает или переносит результат только в рамках согласованного workflow;
8. не читает cookies, пароли, local storage или сессионные хранилища;
9. не обходит авторизацию и не принимает новые OAuth/permission prompts без
   требуемого подтверждения;
10. не считает закрытие вкладки или красивое preview завершённой работой.

Если Grok предлагает подключить GitHub вместо локальной папки, конвейер
останавливается: рабочая копия уже локальная, GitHub не нужен для sync.

---

## 8. Управление Cursor через Computer Use

Перед каждым заданием Codex:

1. проверяет, что Cursor открыт именно в
   `/Users/nateglukhov/analog-horror-site`;
2. читает актуальное состояние приложения;
3. вставляет цельный integration packet без секретов;
4. явно запрещает commit, push, deploy и несвязанный refactor;
5. просит Cursor сначала показать аудит и план затрагиваемых файлов;
6. после каждого существенного UI-действия заново читает состояние Cursor;
7. не переиспользует старые element references или координаты вслепую;
8. сверяет заявления Cursor с локальным `git diff` и тестами;
9. останавливает Cursor при выходе за scope;
10. не разрешает ему отменять или перезаписывать пользовательские изменения.

Cursor может самостоятельно выполнять локальные команды внутри своего агента,
но Codex всё равно повторяет критические проверки в собственной терминальной
сессии.

## 9. Проверка и доказательства

После каждого write-этапа Codex собирает один компактный evidence packet:

- состояние Git до и после;
- список изменённых файлов;
- краткое назначение каждого изменения;
- `git diff --check`;
- `node --check` для изменённых JS;
- целевые validators/smoke с exit code;
- browser QA с route, viewport, visible result и console state;
- известные ограничения;
- решение: `PASS`, `PASS WITH NOTES`, `REWORK` или `BLOCKED`.

Нельзя передавать следующему агенту формулировку «всё работает» без этого
пакета.

## 10. Экономика эксперимента

Codex ведёт простой журнал по каждой волне:

| Метрика | Что считать |
|---|---|
| Human interventions | сколько раз пользователь вручную переносил данные или исправлял курс |
| Agent handoffs | число осмысленных передач между сервисами |
| Rework loops | сколько раз результат возвращался исполнителю |
| Scope violations | несогласованные файлы или действия |
| False completion claims | заявления о тестах без доказательства |
| Wall time | время от task packet до проверенного результата |
| UI failures | потеря вкладки, зависание, устаревшее состояние приложения |
| Accepted output | доля результата, вошедшая в итог без переписывания |

Точный расход токенов фиксируется только там, где сервис его показывает.
Нельзя выдумывать экономию по ощущениям. Полезный итог эксперимента — сравнить:

- число человеческих переключений окон;
- объём повторно переданного контекста;
- количество исправлений после каждого агента;
- время до проверенного, а не заявленного результата.

## 11. Условия аварийной остановки

Codex немедленно ставит конвейер на паузу, если:

- сервис просит пароль, API key, OAuth или новый постоянный доступ;
- обнаружены неожиданные изменения существующих игр;
- два агента редактировали одни файлы одновременно;
- агент пытается сделать commit, push, deploy или публикацию;
- изменены storage keys без миграции;
- Grok или Cursor канонизировал открытый вопрос;
- пропали неизвестные mechanical fields Copy Desk;
- нужно удалить, заменить или пережать исходные медиа;
- тест потребует очистить пользовательский `localStorage` целиком;
- интерфейс больше не позволяет достоверно определить текущий workspace,
  модель или результат операции.

После паузы Codex сообщает пользователю фактическое состояние и самый малый
безопасный способ продолжить.

---

## 12. Первый реальный запуск

Первый запуск мега-плана не начинает писать игру. Он выполняет только нулевой
пилот из раздела 5 и возвращает пользователю:

1. подтверждение доступности Grok и Cursor;
2. read-only отчёт Grok;
3. независимую выборочную проверку Codex;
4. read-only контраудит Cursor;
5. таблицу расхождений;
6. оценку реальной стоимости оркестрации по времени и ручным вмешательствам;
7. рекомендацию, переходить ли к `CONTENT CONTRACT`.

Для начала пилота нужна отдельная явная команда пользователя. До неё Codex не
отправляет задания внешним агентам и не меняет код.
